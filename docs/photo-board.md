# 우리의 사진첩

참가자가 사진 1~3장과 1,000자 이내의 글을 올리는 게시판입니다. 하단 메뉴의 **사진첩**에서 작성자·사진·본문이 이어지는 세로 피드로 봅니다. 여러 장은 피드에서 좌우 스와이프, 화살표, 점 버튼 또는 키보드 방향키로 넘깁니다. 긴 글은 더 보기로 펼치고, 사진을 누르면 크게 볼 수 있습니다. 본인과 추진위원회가 게시글을 삭제할 수 있습니다. 하트로 좋아요를 누르거나 취소할 수 있고, 댓글 버튼으로 500자 이내의 댓글과 답글을 남길 수 있습니다. 피드에는 최근 댓글·답글 3개가 표시되고, 댓글과 답글에도 하트를 누르거나 취소할 수 있습니다. 댓글은 작성자와 추진위원회만 삭제할 수 있습니다. 동영상과 원본 파일 보관은 포함하지 않습니다.

## 비용을 줄이는 기본값

- 사진은 기기에서 JPEG로 변환하며 긴 변 1,600px, 500KiB 이하로 압축합니다. 업로드 미리보기용 360px·50KiB 이하 썸네일도 함께 보관합니다. 캔버스로 다시 인코딩하므로 원본 EXIF 위치 정보를 보관하지 않습니다.
- 한 번에 게시글 18개만 가져오며, 화면 근처의 활성 사진만 읽습니다. 큰 피드에서도 선명하도록 압축한 본 사진을 사용하며, 여러 장을 모두 미리 읽지 않습니다. 넘겨 본 사진은 해당 피드를 벗어날 때까지 재사용합니다. 자동 실시간 구독 대신 새로고침과 더 보기를 제공합니다.
- 개인별 월 30장, 프로젝트 전체 월 1,000장, 전체 보관 4,000장으로 서버에서 제한합니다. 월 기준은 UTC이며, 업로드 예약도 횟수에 포함됩니다. 게시글 삭제나 워크샵 초기화로 월 업로드 한도를 되돌리지 않습니다.
- 저장소는 `kakao-hr-workshop-915-photos`, **US-WEST1 / Standard**입니다. 기존 서울 Firestore·Functions는 그대로 사용합니다. 공개 접근과 객체 ACL을 막고, 삭제 후 추가 보관(soft delete)은 끕니다.
- 사진 데이터는 브라우저와 미국 저장소 사이에서 직접 전송됩니다. Firebase Functions에는 글과 사진 정보만 전달합니다. 서버의 게시 단계에서 저장소 내부 복사가 추가로 발생합니다.
- 무료 제공량은 결제 계정의 다른 사용량과 합산되며 조회·네트워크 초과 비용은 별도입니다. 앱의 업로드 한도는 청구 금액의 상한이나 완전 무료 보장이 아닙니다.

## 좋아요와 댓글

- 좋아요는 참가자별 한 번만 집계하고 원하는 상태(좋아요/취소)를 보내므로 재전송으로 중복 증가하지 않습니다. 피드를 다시 불러오면 다른 기기에서 바뀐 수와 본인의 좋아요 상태도 반영됩니다.
- 댓글은 창을 열 때 원댓글을 최신순 20개씩 가져오고, 답글은 해당 대화를 펼칠 때 20개씩 가져옵니다. 글별 200개·개인별 하루 100개(UTC 기준)로 제한하며, 삭제로 당일 작성 한도를 되돌리지 않습니다. 30일이 지난 댓글 작성 한도 기록은 정리 작업에서 지웁니다.
- 댓글 요청 ID를 유지해 네트워크 재시도 때 중복 게시를 막습니다. 삭제된 댓글은 내용이 없는 작은 기록으로 남겨 이전 요청이 다시 들어와도 되살아나지 않게 합니다. 게시글 삭제 시에는 좋아요·댓글·답글과 각 댓글의 하트 문서까지 삭제합니다.
- 답글은 원댓글 아래 한 단계로 묶어 표시합니다. 답글에 다시 답하면 실제 대상을 `replyToId`로 저장하고 작성자 이름을 표시합니다. 다른 글·다른 대화의 댓글을 답글 대상으로 지정하거나 기존 댓글 ID를 재사용할 수 없습니다.
- 원댓글을 지워도 다른 사람의 답글은 유지합니다. 내용이 없는 ‘삭제된 댓글’ 자리에서 대화를 볼 수 있으며, 마지막 답글까지 삭제하면 자리도 사라집니다. 삭제된 댓글에는 새 하트나 직접 답글을 남길 수 없지만, 남아 있는 답글에는 계속 답할 수 있습니다.
- 피드의 최근 댓글 3개는 댓글·답글 작성/삭제 때 게시글에 함께 저장합니다. 댓글 하트 수가 바뀌면 미리보기도 갱신합니다. 조회 시 본인의 하트 상태만 더해 반환하며, 이전 게시글은 최근 댓글·답글을 읽어 같은 형식으로 표시합니다. 개인별 하트 여부는 공용 미리보기에 저장하지 않습니다.
- 모든 조회·변경은 서버에서 참가자·세션·게시 상태·초기화 세대를 확인합니다. 게시글의 작성자가 다른 참가자의 댓글을 삭제할 수는 없으며, 추진위원회는 모든 댓글을 관리할 수 있습니다.
- 현재 개수는 피드/댓글 새로고침 및 본인의 동작 후에 갱신하며 상시 실시간 구독은 사용하지 않습니다.

## 권한과 업로드 처리

1. `photoBoardAction: begin`이 참가자 존재·세션 버전·워크샵 초기화 세대·월/보관 한도를 Firestore 트랜잭션으로 검증하고 UUID 예약을 만듭니다. 같은 요청 ID의 재시도는 한도를 중복 사용하지 않습니다.
2. 브라우저는 정해진 `photo-uploads/{generation}/{uid}/{postId}/{index}-{full|thumb}.jpg`에만 업로드할 수 있습니다. Storage 규칙이 세션·예약 소유자·사진 수·만료·형식·실제 바이트 수를 검사합니다. 덮어쓰기·임의 경로·직접 삭제·전체 파일 목록은 차단합니다.
3. `publish`가 전체 파일과 JPEG 헤더를 검증한 후, Firebase의 영구 다운로드 토큰이 없는 별도 비공개 `photos/...` 객체로 복사합니다. 임시 업로드 파일을 삭제한 뒤에만 게시글을 공개합니다. Firestore 게시글·통계는 클라이언트가 직접 쓰거나 읽을 수 없습니다.
4. 큰 사진과 썸네일 접근은 `image` 액션이 현재 회원·세션·게시 상태·세대를 확인한 뒤 **5분짜리 GCS 서명 URL**을 발급합니다. Firebase API의 직접 읽기와 영구 다운로드 URL 발급은 차단합니다. 이미 발급된 서명 URL은 최대 5분간 유효하며, 이미 기기에 표시한 사진은 계정 회수로 지울 수 없습니다. 서명 URL과 인증 토큰은 로그에 기록하지 않습니다.
5. 작성자 또는 추진위원회의 삭제 요청은 먼저 게시글을 숨기고 두 경로의 파일을 삭제합니다. 파일과 좋아요·댓글 정리가 끝나면 보관 카운터를 한 번만 반환합니다. 게시 중에는 삭제를 잠시 막아 복사·삭제 간 경합을 방지합니다.
6. 전체 초기화는 이전 세대 게시글을 즉시 숨기고 신규 읽기 URL/업로드를 차단합니다. 매일 실행하는 `cleanupPhotoBoard`가 24시간 이상 방치된 업로드, 미완료 삭제, 이전 세대 게시글을 각 최대 200개씩 정리합니다. 공개된 현재 세대 사진에 자동 보관 만료는 적용하지 않습니다.

미리보기에서는 사진을 브라우저 IndexedDB에 보관합니다. Firebase에는 올리지 않습니다.

## 배포·검증

- `node scripts/photo-storage.cjs`: 사진 저장소 설정 확인.
- `node scripts/photo-storage.cjs --apply`: 기존 Firebase CLI 로그인으로 전용 비공개 저장소 생성, Firebase 연결, 기존 런타임의 객체 관리 권한과 교차 서비스 보안 규칙 권한 설정. 인증 정보는 출력하지 않습니다.
- `firebase deploy --only storage,firestore:indexes,functions:photoBoardAction,functions:cleanupPhotoBoard,functions:workshopAction`: 저장소 규칙·목록 인덱스·새 액션·정리 작업·초기화 연결 배포.
- Storage 서명은 기존 `workshop-runtime`의 자체 서비스 계정 토큰 서명 권한을 사용합니다. 원본 바이트를 서버를 거쳐 전달하는 프록시는 두지 않습니다.
- `npm run test:photos`: Auth·Firestore·Functions·Storage 에뮬레이터에서 소유권, 익명/회수 세션 차단, 업로드 슬롯/크기/형식, 재시도, 한도 동시성, 파일 삭제, 세대 초기화, 페이지네이션, 미완료 업로드 정리를 검사합니다.
- 로컬 브라우저에서 JPG/PNG 선택 → 압축 → 다중 사진 게시 → 큰 사진 탐색 → 삭제를 검증합니다. Storage 에뮬레이터는 실제 GCS 서명을 구현하지 않으므로 운영 환경의 서명·CORS는 별도로 확인합니다.
